  • Du .NET hérité à une application cloud moderne et observable sur Azure App Service
  • Accélération low-code + IA · GitHub Copilot · Application Insights

08 De nouvelles façons de travailler

Contrastez avec le modèle hérité de tickets et de transferts. Tout ce que nous faisons aujourd'hui est reproductible et observable.

09 Ce que « modernisation » signifie vraiment

  • Pas une réécriture par défaut — un éventail d'options
  • Déplacer la charge vers une plateforme qui élimine le travail sans valeur ajoutée
  • Adopter des services gérés pour l'identité, les données et l'observabilité
  • Améliorer la vélocité, la fiabilité, la sécurité et le coût
  • Le résultat avant le livrable — mesurer l'impact métier

Désamorcez la peur que modernisation = réécriture complète. L'essentiel de la valeur vient du rehost/replatform plus des refactorisations ciblées.

10 Pourquoi moderniser maintenant

  • Runtimes et OS en fin de support — risque de sécurité et de conformité
  • Livraisons lentes et manuelles — long délai au changement
  • Difficultés de mise à l'échelle — verticale seulement, capacité fixe
  • Observabilité limitée — délai de détection en heures, pas en secondes
  • Coût — payer pour des VM surdimensionnées et inactives

Faites nommer par la salle le facteur le plus criant. Vous le relierez à une capacité App Service ou App Insights.

11 Le paysage des plateformes applicatives Azure

  • App Service — applications web et API gérées, voie la plus rapide pour .NET
  • Azure Container Apps — conteneurs serverless, mise à l'échelle à zéro, microservices
  • AKS — Kubernetes complet pour un contrôle maximal
  • Azure Functions — serverless événementiel à la consommation
  • Cible du jour : App Service exécutant des conteneurs .NET depuis ACR

Dimensionnez la plateforme selon l'équipe. Nous avons choisi App Service pour MAPAQ : simplicité PaaS, souplesse des conteneurs, mise à l'échelle et diagnostics intégrés.

13 Prendre une décision éclairée

  • Évaluer : version du runtime, dépendances, état, gravité des données
  • Noter chaque app : valeur métier × risque technique
  • Choisir le R le moins coûteux qui débloque le résultat métier
  • Le prouver de bout en bout sur une app avant de généraliser
  • Outils : .NET Upgrade Assistant + agent de modernisation GitHub Copilot

La décision est itérative et non linéaire : on peut rehoster d'abord, refactoriser ensuite. Aujourd'hui MAPAQ est notre application de preuve.

15 Accélérer avec le low-code + l'IA

  • Low-code (Power Platform) pour les apps périphériques, portails et flux
  • Le codage assisté par IA déplace l'effort de la frappe vers la revue
  • Copilot pour le code, les tests et la documentation au quotidien
  • Agents spécialisés pour les mises à niveau et migrations complètes
  • L'humain garde le contrôle — réviser chaque changement

Positionnez l'IA comme un multiplicateur de force, pas un remplacement. L'agent de modernisation montré ensuite fait le travail lourd et répétitif.

17 Modernisation d'applications .NET avec GitHub Copilot

  • Installée comme extension VS Code dans cet atelier
  • Évalue la solution et propose un plan de mise à niveau
  • Automatise les mises à niveau de framework cible et de paquets

24 App Service — les paramètres qui comptent

  • Always On = activé — garde l'app au chaud (réglé sur MAPAQ)
  • Chemin de contrôle d'intégrité = /healthz — les instances malsaines sont retirées
  • HTTPS uniquement, TLS minimum = 1.2, FTP = désactivé
  • Pile/runtime — ici un conteneur personnalisé, pas une pile intégrée
  • Identité gérée — l'app s'authentifie auprès de SQL, ACR et App Insights

Ce sont les vrais paramètres de production de mapaq-web. Expliquez chaque choix de durcissement.

25 Configuration et variables d'environnement

  • Les App Settings injectent la configuration comme variables d'environnement
  • Clés réelles : APPLICATIONINSIGHTS_CONNECTION_STRING, ApplicationInsights__ConnectionString
  • Ingestion par identité : APPLICATIONINSIGHTS_AUTHENTICATION_STRING + AZURE_CLIENT_ID
  • ConnectionStrings__MapaqSql, MapaqApi__BaseAddress, WebOrigin
  • Conteneur : DOCKER_REGISTRY_SERVER_URL, WEBSITES_PORT, OTEL_RESOURCE_ATTRIBUTES

POINT DE RÉCONCILIATION IMPORTANT : l'app en direct utilise l'IDENTITÉ GÉRÉE pour l'ingestion App Insights (la paire AUTHENTICATION_STRING + AZURE_CLIENT_ID), et les clés à double souligné mappent vers les sections de config .NET. Les espaces réservés du appsettings.json du dépôt sont vides à dessein — les vraies valeurs sont injectées ici par le pipeline. Montrez l'onglet Variables d'environnement en direct.

26 Environnements et emplacements de déploiement

  • Environnements App Service séparés par étape : dev / test / prod
  • Emplacements de déploiement = copies de préproduction sur le même plan
  • Préchauffer un emplacement puis le permuter avec quasi-zéro interruption
  • Les paramètres collants à l'emplacement restent en place lors d'une permutation
  • Modèle : déployer en préproduction → test de fumée → permuter en production

rg-dev-001 est l'environnement dev. Expliquez comment les mêmes Bicep + azd promeuvent vers test/prod en changeant l'environnement. Mentionnez la permutation d'emplacement pour des livraisons sûres.

27 Exécuter .NET en conteneurs sur App Service

  • Source de l'image : Azure Container Registry (acr…azurecr.io/mapaq-web:<sha>)
  • Déploiement continu depuis ACR à chaque nouvelle image
  • WEBSITES_PORT indique à App Service le port du conteneur
  • Tirage authentifié via l'identité gérée de l'app (aucun identifiant admin)
  • La même image tourne en local, en CI et dans Azure — parité

Ouvrez Centre de déploiement → paramètres de conteneur. Montrez que l'étiquette d'image est un SHA git. Voilà l'histoire « avec conteneurs » : construire une fois, promouvoir l'artefact.

28 Flux de journaux — journaux d'application en direct

  • Surveillance → Flux de journaux affiche stdout/stderr en temps réel
  • Activer les journaux App Service (système de fichiers) pour déboguer vite
  • Les journaux de conteneur montrent démarrage, contrôle d'intégrité et requêtes
  • Idéal pour les moments « est-ce que ça démarre seulement ? » lors d'un déploiement
  • Pour une analyse durable, envoyez vers Log Analytics / App Insights

DÉMO. Ouvrez le Flux de journaux, puis frappez l'URL de l'app et regardez défiler les requêtes. Contrastez le flux éphémère avec la télémétrie durable dans App Insights.

29 Mise à l'échelle verticale (instances plus grandes)

  • Scale up = changer le niveau/la taille du plan App Service
  • Plus de CPU, de mémoire et de fonctionnalités par instance
  • Plan actuel : P1v3 — possibilité de passer à P2v3 / P3v3
  • Les niveaux Premium débloquent l'intégration VNet, plus d'emplacements, l'auto-scale
  • Montez en gamme quand une requête est gourmande en ressources

Ouvrez Scale up (plan App Service). Montrez la grille de niveaux. Insistez : monter en gamme change la taille de chaque instance — c'est au niveau du plan et affecte toutes les apps du plan.

30 Mise à l'échelle horizontale (plus d'instances)

  • Scale out = exécuter plus de copies de l'app derrière l'équilibreur
  • Manuel : fixer un nombre d'instances
  • Automatique : auto-scale basé sur des règles (plans Premium)
  • Montez en nombre pour le débit et la résilience
  • Les apps sans état montent proprement — gardez l'état de session externe

Ouvrez Scale out. Montrez d'abord le nombre manuel, puis basculez vers Auto-scale personnalisé pour la diapositive suivante. Les apps MAPAQ sont sans état, donc elles montent en toute sécurité.

34 Instrumentation API + SQL

  • Le même SDK AI sur Mapaq.Api
  • Les appels SQL EF Core 10 sont suivis comme dépendances SqlClient
  • HttpClientFactory propage traceparent vers les appels en aval
  • Événements personnalisés : TelemetryClient.TrackEvent avec dimensions personnalisées

L'instrumentation EF Core → SqlClient est livrée avec le SDK; aucun paquet additionnel. Voilà comment le span SQL apparaît dans la cascade.

35 W3C Trace Context — traceparent

  • Format : 00-{trace-id}-{parent-id}-{flags}
  • Le SDK navigateur démarre la trace et émet l'en-tête sur chaque fetch/XHR
  • ASP.NET Core l'honore et le transmet automatiquement
  • Résultat : un seul operation_Id relie les quatre spans

Ouvrez les outils de dev → Réseau → une requête → En-têtes, et montrez le vrai traceparent. C'est le fil qui relie toute l'histoire.

37 Corrélation navigateur

  • Ajouter le SDK JavaScript Application Insights à _Layout.cshtml
  • Passer la chaîne de connexion via ViewData côté serveur — jamais en dur
  • enableCorsCorrelation: true et enableRequestHeaderTracking: true
  • distributedTracingMode: AI_AND_W3C pour émettre traceparent

Le snippet doit se charger avant tout script qui émet fetch/XHR, sinon les premières pages vues sont perdues.

38 SDK navigateur — configuration minimale

  • Utiliser connectionString (instrumentationKey est déprécié)
  • enableAutoRouteTracking: true pour la navigation type SPA
  • correlationHeaderExcludedDomains pour les hôtes tiers
  • samplingPercentage: 100 en dev, plus bas en prod

L'échantillonnage se règle sur l'objet d'options du SDK, par app — pas dans le portail.

41 Recherche de transactions et vue de bout en bout

DÉMO. La carte d'application découvre la topologie depuis la télémétrie — sans config. Cliquez un nœud pour voir performance et échecs de ce composant.

43 Panneaux Échecs et Performance

  • Échecs — opérations en échec, codes de réponse, types d'exception
  • Performance — opérations les plus lentes, durée des dépendances, p50/p95/p99
  • Passer d'un agrégat directement aux transactions échantillons
  • Trier par impact utilisateur d'abord, puis par cause

DÉMO. Si possible, forcez un 5xx (arrêtez l'API ou frappez une mauvaise route) et regardez Échecs s'allumer, puis plongez dans l'exception.

44 Journaux (KQL) — une requête, un operation_Id

  • Ouvrir le panneau Journaux sur la ressource App Insights
  • union requests, dependencies, pageViews
  • Filtrer par operation_Id, projeter les colonnes clés, trier par temps
  • Le résultat est la même cascade, en données qu'on peut grapher et exporter

DÉMO. Exécutez la requête de la diapositive suivante. L'union entre tables est l'astuce que les débutants manquent.

45 Requête KQL — à copier / coller

  • union requests, dependencies, pageViews
  • | where operation_Id == 'COLLER-OPERATION-ID'
  • | project timestamp, itemType, name, duration, success, target
  • | order by timestamp asc

Récupérez l'operation_Id depuis le traceparent dans les outils de dev ou la Recherche de transactions, collez-le et exécutez. Sauvegardez la requête dans le classeur.

46 Classeurs — tableaux de bord partageables

  • Classeur pré-construit : volume 24 h, latence p95, % d'échec, top dépendances
  • Paramétré par nom de rôle et plage de temps
  • Mélange KQL, métriques, texte et paramètres dans un document
  • Importable en JSON — pas besoin de Power BI

DÉMO. Ouvrez le classeur, changez la plage de temps et le paramètre de rôle, et montrez la mise à jour des visuels. Mentionnez qu'ils sont versionnables en JSON.

47 Créer des éléments de travail depuis Application Insights

  • Configurer une intégration d'éléments de travail (Azure DevOps / GitHub)
  • Depuis un échec ou une transaction, cliquer « Créer un élément de travail »
  • Le contexte de télémétrie (operation_Id, pile, version) est joint
  • Boucle complète : détecter → déclarer → corriger → vérifier
  • Notre flux ADO : Epic → Feature → User Story/Bug, étiquette « Agentic AI »

DÉMO. Montrez l'intégration d'éléments de travail sur la ressource App Insights, puis créez un bug depuis un vrai échec. Soulignez comment le contexte de télémétrie arrive sur l'élément pour qu'un développeur le reproduise.

48 Journalisation locale vs distante

  • Locale : console ILogger + Flux de journaux App Service pour un retour rapide
  • Distante : ILogger → Application Insights en traces (durable, interrogeable)
  • Journalisation structurée — les propriétés deviennent des dimensions en KQL
  • Corrélation : les journaux portent le même operation_Id que la requête
  • Régler les niveaux via appsettings + le LoggerProvider ApplicationInsights

DÉMO. Émettez un journal structuré en local et observez-le dans la console, puis retrouvez la même entrée dans les traces App Insights filtrées par operation_Id. Voilà l'histoire de la journalisation locale et distante.

49 Alertes et détection intelligentes

  • Smart Detection trouve automatiquement les anomalies de taux d'échec et de latence
  • Alertes de métrique sur disponibilité, temps de réponse, requêtes en échec
  • Groupes d'actions → courriel, SMS, Teams/webhook ou automatisation
  • Alerter sur les symptômes (impact utilisateur), pas seulement les causes

DÉMO. Montrez les paramètres de Smart Detection et créez une alerte de métrique (ex. requêtes en échec > N sur 5 min) reliée à un groupe d'actions.

50 Démo — App Insights, quoi montrer

  • 1 · Live Metrics pendant que la salle charge l'app
  • 2 · Recherche de transactions → cascade de bout en bout
  • 3 · Carte d'application → cliquer le nœud SQL
  • 4 · Échecs → plonger dans une exception → créer un élément de travail
  • 5 · Journaux (KQL) → classeur → une alerte

Liste de contrôle maîtresse pour l'heure. Gardez le trafic actif tout du long. Utilisez scripts/open-monitoring-dashboard.ps1 pour sauter à la ressource.

51 Contrôle des coûts — pas de surprises

  • Plafond quotidien sur la ressource App Insights pour l'atelier
  • Échantillonnage : 100 % en dev, 10–25 % typique en prod
  • L'AI basé sur espace de travail utilise les niveaux d'engagement Log Analytics
  • Bien dimensionner le plan App Service; réduire quand inactif
  • Étiqueter tout pour découper la facturation

Reliez le coût aux leviers de mise à l'échelle et d'échantillonnage vus plus tôt. Le plafond quotidien protège l'abonnement.

52 Liste de dépannage

  • Pas de télémétrie ? Vérifier APPLICATIONINSIGHTS_CONNECTION_STRING dans App settings
  • Ingestion par identité en échec ? Vérifier AZURE_CLIENT_ID + AUTHENTICATION_STRING + attribution de rôle
  • Conteneur ne démarre pas ? Confirmer WEBSITES_PORT et l'étiquette d'image dans le Centre de déploiement
  • PageViews manquantes ? Le snippet doit se charger avant les autres scripts
  • Dépendances SQL manquantes ? EF Core a besoin du SDK AI — le paquet seul ne suffit pas

Gardez cette diapositive visible pendant les ateliers. La plupart des questions correspondent à une de ces lignes. La ligne identité est spécifique à la configuration de rg-dev-001.

53 Démantèlement

  • azd down --purge --force
  • --purge retire les Key Vault et ressources AI supprimés en douceur
  • --force saute la confirmation interactive
  • Vérifier que le groupe de ressources a disparu dans le portail

Démontrez toujours le démantèlement en direct. Un atelier sans démantèlement est une bombe de facturation. (À sauter sur rg-dev-001 partagé s'il doit persister.)
