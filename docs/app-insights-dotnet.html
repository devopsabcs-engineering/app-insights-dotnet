08 New ways of working

  • Trunk-based, small PRs, automated checks

  • AI in the loop — Copilot for code, modernization agent for upgrades
  • You build it, you run it — dev and ops share the dashboard

Contrast with the legacy ticket-and-handoff model. Everything we do today is reproducible and observable.

09 What 'modernization' actually means

  • Not a rewrite by default — a spectrum of options
  • Move the workload to a platform that removes undifferentiated heavy lifting
  • Adopt managed services for identity, data, and observability
  • Improve developer velocity, reliability, security, and cost
  • Outcome over output — measure business impact

Defuse the fear that modernization = full rewrite. Most value comes from rehost/replatform plus targeted refactors.

10 Why modernize now

  • End-of-support runtimes and OS — security & compliance risk
  • Slow, manual releases — long lead time to change
  • Scaling pain — vertical-only, fixed capacity, weekend firefights
  • Limited observability — mean-time-to-know is hours, not seconds
  • Cost — paying for idle, oversized VMs

Have the room call out which driver is loudest for them. You will tie each back to an App Service or App Insights capability.

11 The Azure app platform landscape

  • App Service — managed web apps & APIs, fastest path for .NET
  • Azure Container Apps — serverless containers, scale-to-zero, microservices
  • AKS — full Kubernetes when you need maximum control
  • Azure Functions — event-driven, consumption serverless
  • Today's target: App Service running .NET containers from ACR

Right-size the platform to the team. We chose App Service for MAPAQ: PaaS simplicity, container flexibility, built-in scale and diagnostics.

13 Making an informed decision

  • Assess: runtime version, dependencies, statefulness, data gravity
  • Score each app: business value × technical risk
  • Pick the lowest-effort R that unblocks the business outcome
  • Prove it on one app end-to-end before scaling the pattern
  • Tools: .NET Upgrade Assistant + GitHub Copilot modernization agent

Decision-making is iterative and non-linear: you may rehost first, then refactor later. Today MAPAQ is our proof app.

24 App Service — settings that matter

  • Always On = On — keeps the app warm (set on MAPAQ)
  • Health check path = /healthz — unhealthy instances are removed
  • HTTPS only, Minimum TLS = 1.2, FTP state = Disabled
  • Stack/runtime — here it's a custom container, not a built-in stack
  • Managed identity — the app authenticates to SQL, ACR, and App Insights

These are the actual production settings on mapaq-web. Explain why each hardening choice was made.

25 Configuration & environment variables

  • App settings inject configuration as environment variables
  • Live keys: APPLICATIONINSIGHTS_CONNECTION_STRING, ApplicationInsights__ConnectionString
  • Identity-based ingestion: APPLICATIONINSIGHTS_AUTHENTICATION_STRING + AZURE_CLIENT_ID
  • ConnectionStrings__MapaqSql, MapaqApi__BaseAddress, WebOrigin
  • Container: DOCKER_REGISTRY_SERVER_URL, WEBSITES_PORT, OTEL_RESOURCE_ATTRIBUTES

IMPORTANT reconciliation point: the live app uses MANAGED IDENTITY for App Insights ingestion (the AUTHENTICATION_STRING + AZURE_CLIENT_ID pair), and the double-underscore keys map to .NET config sections. The repo appsettings.json placeholders are intentionally empty — real values are injected here by the pipeline. Show the Environment variables tab live.

26 Environments & deployment slots

  • Separate App Service environments per stage: dev / test / prod
  • Deployment slots = staging copies on the same plan
  • Warm up a slot, then swap with near-zero downtime
  • Slot-sticky settings stay put across a swap
  • Pattern: deploy to staging → smoke test → swap to production

rg-dev-001 is the dev environment. Explain how the same Bicep + azd promotes to test/prod by changing the environment. Mention slot swap for safe releases.

27 Running .NET in containers on App Service

  • Image source: Azure Container Registry (acr…azurecr.io/mapaq-web:<sha>)
  • Continuous deployment from ACR on new image push
  • WEBSITES_PORT tells App Service which container port to bind
  • Pull authenticated via the app's managed identity (no admin creds)
  • Same image runs locally, in CI, and in Azure — parity

Open Deployment Center → Container settings. Show the image tag is a git SHA. This is the 'using containers' story: build once, promote the artifact.

29 Scale up — vertical (bigger instances)

  • Scale up = change the App Service Plan tier/size
  • More CPU, memory, and features per instance
  • Current plan: P1v3 — can move to P2v3 / P3v3
  • Premium tiers unlock VNet integration, more slots, autoscale
  • Scale up when a single request is resource-hungry

Open Scale up (App Service plan). Show the tier grid. Emphasize: scaling up changes the size of each instance — it's a plan-level change that affects all apps on the plan.

30 Scale out — horizontal (more instances)

  • Scale out = run more copies of the app behind the load balancer
  • Manual: set a fixed instance count
  • Automatic: rules-based autoscale (Premium plans)
  • Scale out for throughput and resilience
  • Stateless apps scale out cleanly — keep session state external

Open Scale out. Show manual instance count first, then switch to Custom autoscale for the next slide. MAPAQ apps are stateless, so they scale out safely.

34 API + SQL instrumentation

  • Same AI SDK on Mapaq.Api
  • EF Core 10 SQL calls auto-tracked as SqlClient dependencies
  • HttpClientFactory propagates traceparent to downstream calls
  • Custom events: TelemetryClient.TrackEvent with custom dimensions

EF Core → SqlClient instrumentation ships with the SDK; no extra package. This is how the SQL span appears in the waterfall.

35 W3C Trace Context — traceparent

  • Format: 00-{trace-id}-{parent-id}-{flags}
  • Browser SDK starts the trace and emits the header on every fetch/XHR
  • ASP.NET Core honours and forwards it automatically
  • Result: one operation_Id stitches all four spans together

Open browser DevTools → Network → a request → Headers, and show the real traceparent. This is the thread that ties the whole story together.

37 Browser correlation

  • Add the Application Insights JavaScript SDK to _Layout.cshtml
  • Pass the connection string via server-side ViewData — never hard-code
  • enableCorsCorrelation: true and enableRequestHeaderTracking: true
  • distributedTracingMode: AI_AND_W3C to emit traceparent

The snippet must load before any script that issues fetch/XHR, or early page views are lost.

38 Browser SDK — minimal config

  • Use connectionString (instrumentationKey is deprecated)
  • enableAutoRouteTracking: true for SPA-style navigation
  • correlationHeaderExcludedDomains for third-party hosts
  • samplingPercentage: 100 in dev, lower in prod

Sampling is set on the SDK options object, per app — not in the portal.

44 Logs (KQL) — one query, one operation_Id

  • Open the Logs blade on the App Insights resource
  • union requests, dependencies, pageViews
  • Filter by operation_Id, project the key columns, order by time
  • The result is the same waterfall, as data you can chart and export

DEMO. Run the query on the next slide. The union across tables is the trick newcomers miss.

45 KQL query — copy / paste

  • union requests, dependencies, pageViews
  • | where operation_Id == 'PASTE-OPERATION-ID'
  • | project timestamp, itemType, name, duration, success, target
  • | order by timestamp asc

Grab the operation_Id from the traceparent in DevTools or from Transaction Search, paste it in, and run. Save the query to the workbook.

48 Local vs remote logging

  • Local: ILogger console + App Service Log stream for fast feedback
  • Remote: ILogger → Application Insights as traces (durable, queryable)
  • Structured logging — log properties become custom dimensions in KQL
  • Correlation: logs carry the same operation_Id as the request
  • Set levels via appsettings + ApplicationInsights LoggerProvider

DEMO. Emit a structured log locally and watch it in the console, then find the same entry in App Insights traces filtered by operation_Id. This is the local-and-remote logging story.

52 Troubleshooting checklist

  • No telemetry? Verify APPLICATIONINSIGHTS_CONNECTION_STRING in App settings
  • Identity ingestion failing? Check AZURE_CLIENT_ID + AUTHENTICATION_STRING + role assignment
  • Container won't start? Confirm WEBSITES_PORT and the image tag in Deployment Center
  • Browser pageViews missing? Snippet must load before other scripts
  • SQL deps missing? EF Core needs the AI SDK — package alone is not enough

Keep this slide visible during labs. Most questions map to one of these lines. The identity line is specific to how rg-dev-001 is configured.
